# Why the corner post was not working

Read-only diagnosis, 2 Oct 2026, from the live database and the source. Every probe
carried a positive control and a canary; all held. Nothing was edited, built or run.

---

## 1. The direct cause: the joint is ONE-SIDED

A joint is a shared UUID that must appear on BOTH runs. On the Makayla job only one
end carries one:

| Run | start_joint | end_joint |
|---|---|---|
| Left Side (74 ft, 6 ft) | *blank* | *blank* |
| Back (50 ft, 4 ft) | *blank* | *blank* |
| Right side (72 ft, 6 ft, gate) | *blank* | `92dff4e0…` |

Only one row in the whole table carries `92dff4e0…` (control 1, canary 0). Its
partner does not exist.

`RunJoinArithmetic.adjust` (`geometry/FenceGeometry.kt:830`) groups by the id, finds
one live member, and records `FEWER_THAN_TWO_LIVE_RUNS` (`:852`) — **no adjustment**.
Suggest therefore returns un-joined counts, which is exactly what is stored:
END_POST 2 + 3 + 2, zero CORNER_POST.

Right's points end at `6000.28:803.1039`, which is **exactly** Back's start. Left and
Back also meet at a point. The geometry is right; the record of it is not.

### What this corrects

`docs/MAKAYLA_QUOTE_READY.md` says "Both corners on this job ARE attached in the
data." The live database contradicts that. Either `supabase_a78_join_makayla_corners.sql`
never ran, or a phone push blanked it — see §3.

## 3. Why it will keep happening — five real defects

**(a) A one-sided joint is a legal state.** Detach writes one end blank and leaves the
partner's id stranded (`ui/survey/SurveyViewModel.kt:1565-1567`). Undo/redo frees only
the run's own end (`:426`, called at `:946` and `:991`).

**(b) A stale phone row can erase a cloud joint.** The push is row-level
last-writer-wins on `run.updatedAt > cloud stamp` (`EntitySync.kt:3905`) and sends
blank joints. There is no field-level merge.

**(c) The screen says "Joined to a corner" when NOTHING is stored.** A point dropped
within snap reach is moved exactly onto the target vertex and a green hint reads
"Joined to a corner" (`strings.xml:295`, shown at `SurveyDrawScreen.kt:2741`). No joint
is written at that moment — the only writers are `acceptSnapJoinOffer` (`:1499`),
`confirmJoinOffer` (`:1559`) and the undo path. **This is almost certainly what was
seen.**

**(d) The snap reach is far too small to hit on purpose.** 26 canvas units
(`FenceGeometry.kt:442`) = **0.33 to 1.3 ft** depending on grid extent, about
**3.5 screen px at zoom 1**. A normal drag misses, so no offer is ever raised.

**(e) A catch-22 between the two join paths.** Attach mode refuses any gap over 2.0 ft
with "drag it over first" (`FenceGeometry.kt:1285`), but the drag it recommends must
land within 0.33–1.3 ft. **On the 400 ft grid, ends 3 ft to ~15 ft apart cannot be
joined at normal zoom by either route.**

## 4. Why the price moves on its own

This is the "calculations keep changing" complaint, and it has concrete causes:

1. **Suggest is per run, but a joint changes every member run.** The taller run owns
   the shared post. With both corners attached, the 4 ft Back would have zero end posts
   AND zero corner posts. Pressing Suggest on Back alone drops its end posts and adds no
   corner anywhere — **the job gets cheaper**. `repriceEveryRun` (`SurveyViewModel.kt:1653`)
   covers this only after the in-app join gesture, never after a pull or a SQL write.
2. **Drawing on from a joined tip moves the joint to the new tip.** `addDrawPoint` calls
   `writePoints` and never touches the joint, so a post is shared between ends that are
   now far apart. One live joint holds its two ends **110.6 ft** apart.
3. **Dragging or retyping the length of a joined end leaves the partner behind** and
   keeps the joint. Only undo and redo free joints.
4. **A type or height change re-prices only that run.** The shared-post owner is picked
   across runs by `joinHeightOf` (`EstimateEngine.kt:732`) and `outranks`
   (`FenceGeometry.kt:~933`). Changing run A can move the post to neighbour B, whose
   takeoff is never rewritten.
5. **Height edits do not re-price at all.** `RunEditViewModel.update` (`:192-196`)
   writes the row and stops.
6. **`confirmJoinOffer` calls `repriceEveryRun` without awaiting the end move**
   (`:1597` then `:1607`), so it can price the old geometry.

## 5. Fence type per line

**It cannot be done from the grid today.**

- `SideTypesCard` (`ui/runs/SideTypesCard.kt:64`) is written but **mounted nowhere**.
  Grep finds only its own declaration, comments and a test constant; the search was
  proven against `snapJoinOffer`, which hits 7 times in the same file. Test `a81:5d`
  only checks the file's text mentions `FenceTypeDropdown` — nothing asserts it is on a
  screen.
- The only place a type can be changed is `RunEditScreen` (`MainActivity.kt:749`),
  reachable only from the job screen's run list. The drawing screen cannot navigate to it.
- Other runs are drawn faded and **non-interactive** (`SurveyDrawScreen.kt:1531-1544`),
  and there is no hit-test on a run's line, so there is nothing to tap.
- Lines are coloured only by `isTeardown`, so the grid gives no cue which side is which type.
- A "line" is a whole run (a polyline). Consecutive taps extend one run, so a stretch
  with its own type must be its own run.

### Pricing gaps found alongside it

- **A 4 ft vinyl side with corners bills the 6 ft corner post.** The catalog has a
  single VINYL `CORNER_POST` row, declared 6 ft. Line, end and gate posts correctly
  declare both 4 and 6.
- **No ALUMINUM, IRON, CHAIN_LINK, WOOD, COMPOSITE or SPLIT_RAIL post row declares a
  height at all**, so the height filter (`EstimateEngine.kt:1305-1315`) is inert for
  every type except vinyl.
- **Chain link posts filter on `panelHeightFt`, not `fabricHeightFt`**, and editing the
  fabric height leaves `panelHeightFt` stale — so the filter never bites.
- **A new side drawn on the grid gets the wrong post spacing.** `createBlankRun`
  (`SurveyViewModel.kt:1933`) inherits the type but then copies spacing from the profile
  instead of `RunTypeChange.spacingFor`, so a new wood side gets 6 ft spacing instead of
  8. The job screen's `addRun` does this correctly.

## 7. The calculations: the arithmetic is NOT random

Proven, not assumed:

- **Priced twice from identical input: byte-identical.** 0 of 85 fixtures differ.
- **Inputs shuffled** (catalog, existing lines, runs, change orders): 0 of 85 change.
- **Commit and re-price, 5 cycles**: 0 of 85 drift.
- **All 17 live jobs replayed twice through the real loader and engine**: 0 differ.
- Controls held: a tax or labour mutation changed the output in 85 of 85.
- No clock, no random, no UUID anywhere in the pricing path. Line ids are content hashes.

**What actually moves the number is that stored lines are a snapshot, refreshed only on
some edits and only per run.** Ranked:

1. **Spec edits on the run-edit screen never re-price.** `RunEditViewModel.update`
   (`:35-39`) writes the row and stops. Panel width, panel height, post spacing,
   concrete bags, colour, rail counts and teardown all go through it. Only
   `setFenceType` re-prices. Meanwhile the Estimate screen's `takeoff` readout
   (`EstimateViewModel.kt:74`) is a **live recompute**, so it disagrees with the stored
   lines and the totals until Suggest is pressed. **That is the number appearing to
   change by itself.**
2. **Re-pricing is per run; the shared post is decided across runs.** Simulated on the
   server engine: a stale partial total of $4,951.90 against a full reprice of
   $4,928.31 — a **$23.59 double-counted post**. `deleteFenceRun` frees the partner's
   joint (`Repository.kt:774-776`) with no re-price, so the partner keeps its given-up
   end post and stays one post short.
3. **Catalog and engine changes move nothing until a run regenerates, then jump.**
   Live replay: **3 of the 6 jobs with stored lines differ from a fresh reprice by
   +$43.04, +$148.28 and +$489.18 — and two of those three are ACCEPTED jobs.**
   Causes in the stored rows: LINE_POST at $13.18 against a fresh $16.56, END_POST
   quantity 5 against 3, and BLANK_POST/GATE_POST absent entirely.
4. **The join post kind flips at exactly 15°.** x=267 (14.95°) gives LINE, x=268
   (15.00°) gives CORNER; counts move 29/1 to 28/2. A one-pixel drag changes the bill.
5. **Waste silently vanishes on PANEL** when the chosen catalog row's width differs
   from the run's spec width (`EstimateEngine.kt:1373`, `line-items.ts:326-331`).
   10% waste on a 175 ft run: **33 panels when the row matches, 22 when it doesn't** —
   and 22 is exactly the zero-waste figure. Both engines agree, so it is not a
   phone-versus-office split.
6. **Joins are covered by ZERO parity fixtures** (0 of 85 carry a joint) and **no Kotlin
   test calls the join arithmetic at all**. `a33` compares against a frozen snapshot of
   Kotlin's own output, so a later Kotlin edit passes it unnoticed.
7. **The flip-flop is real and logged.** 201 `estimate_line_items.quantity` changes on
   53 lines over 14 days, **78 of them reverts to the previous value**. Since 1 Oct:
   one actor, 3 jobs, 18 lines, 23 reverts, 17 within 60 seconds of the previous change.
   None on hand-edited lines.
8. **`quote-view` falls back to `subtotal + tax` — no labour, no markup, no discount —**
   when `contract_total` is missing (`S/quote-view/index.ts:388`). Live: 4 of 17 jobs
   have a quote link with no `contract_total`, and 1 of those has lines.
