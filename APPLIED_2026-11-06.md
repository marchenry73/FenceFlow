## 1. Crew job scope is applied

March asked for it "on the sandbox first". **That is not possible and I said
so before applying it**: there is one database, and this migration creates
tables, functions, policies and views, which are schema-wide. The sandbox is a
tenant, not a schema. What I did instead was fingerprint every real login's
job visibility before and after, and prove the two are identical.

### Applied as one transaction

The file carries no transaction control of its own -- `tests/crew-job-scope.test.mjs`
supplies the `begin;` -- so it was wrapped in an explicit `begin; ... commit;`
together with its ledger correction, so the change and the record of it cannot
disagree. Its own self-check raises on any problem, which would have rolled
back both.

File sha256 `5aa350f213a3b0f0884d5461c92a40cc1bffcc4a60f9ac9c1fd7f805fad6ed05`,
matching what the ledger had recorded, so the file had not changed since.

### Verified afterwards, from the database

| claim | got | want |
|---|---|---|
| `job_assignments` table exists | 1 | 1 |
| the 15 new functions exist | 15 | 15 |
| four crew views are security barriers | 4 | 4 |

`anon` was checked deliberately: Supabase's default privileges hand every new

Compared as multisets, so the two identical Legacy Solutions OWNER rows are
both accounted for; a first attempt keyed on (company, role) collapsed them and
a second keyed on a `uid` column the output did not contain, which made ten
rows compare as one and pass vacuously. The comparison was then checked by
tampering with a row and confirming it reports a difference.

**Two measurement traps, both hit and both caught by the same control.**
The control row is what postgres sees with RLS bypassed, and at least one
login must see fewer.

1. A plain `select` with `set_config('role','authenticated')` in its FROM
   clause returned **everything** for all nine logins -- RLS is bound at plan
   time, so switching role mid-statement changes nothing. The control caught it
   because every login matched the postgres set exactly.
2. Before that, a shell harness reported `QUERY_FAILED` for all ten rows,
   including the control, because a grep pattern missed the space in
   `"rows": [`.

The working method is the repo's own idiom, from
`supabase_crew_job_scope_probe.sql`: inside plpgsql, `set local role
authenticated` and then run the query through `EXECUTE`. Dynamic SQL is planned
after the switch, so RLS applies.

### The feature is not inert

"Nothing moved" is also what a migration that did nothing would produce, so:
`supabase_crew_job_scope_probe.sql` run against the live schema (and rolled
back) reports **189/189**. In it a scoped crew member sees `A` where the office
sees `A,B,F,N,Q,U,X` -- one job against seven. The probe's tally counts a
`want` as met on exact equality, an `ERR ` prefix, or a `~` regex.

Nothing survived: 0 `job_assignments` rows, 0 probe companies, 0 access
requests, still exactly 20 live jobs.

### Why applying it was safe, measured not assumed

The migration states its own rule: *"WHO SEES EVERY JOB: a capability test,
never a role test"* -- `sees_all_jobs()` is `SEE_MONEY or EDIT_JOBS or
SCHEDULE_AND_ASSIGN`. Employee records do not enter into it.

All nine logins: 8 OWNER, 1 MANAGER, `permission_overrides` empty on every one.
**Zero CREW logins exist.** The one non-owner was checked by impersonating it
and calling the live `has_permission` directly: `SEE_MONEY` true, `EDIT_JOBS`
true, `SCHEDULE_AND_ASSIGN` true, and `RECORD_REFUNDS` **false** -- that last
one proving the impersonation took effect rather than the function answering
true to everything.

The migration's own "who is not linked yet" query agrees: 0 crew logins and 0
unlinked crew logins in every company.

**The sequencing rule still applies going forward.** The first crew login
March creates needs a linked crew record and job assignments, or that person
sees nothing. It is a rule for when he hires, not a blocker now.

## 2. DEFECT: the ledger claimed this migration was already live

`public.schema_migrations` recorded `supabase_crew_job_scope.sql` as
`origin='adopted'` at 2026-11-05 23:54:44. "Adopted" is defined in that table
as *already live, so recorded without running*. For this file it was false:
neither `job_assignments` nor `sees_all_jobs()` existed, so it had never run.

The runner therefore reported **`pending = 0`** while a migration in its own
list was outstanding -- an empty answer reading as good news.

The cause is the adoption sweep itself: it recorded all 208 unapplied files in
`apply-order.txt` as adopted **without checking whether each was actually
live**. This file's row is now corrected to `applied` with a note.

**The other 207 rows carried the same unverified claim, so they were checked.**
`scripts/ledger-liveness.mjs` reads each adopted file, extracts the objects it
would create, and asks the catalog whether they exist:

| verdict | n |
|---|---|
| LIVE -- every object it creates exists | 179 |
| NOT LIVE -- none of them do | 1 |
| PARTIAL -- some do | 6 |
| UNJUDGEABLE -- creates no checkable object | 21 |
| file named but not on disk | 0 |

**Nothing else is in the state crew_job_scope was in.** The one NOT LIVE is a
supersession, not a gap: `supabase_webhook_patch.sql` creates a trigger named
`job_change_push`, and the live trigger is the hyphenated `job-change-push`
created by `supabase_narrow_push_trigger.sql`, which reads LIVE. The six
PARTIAL rows are the same shape -- `companies_platform_admin_all` is live as
`companies_platform_admin_read`, `jobs_crew_view` as `jobs_crew` -- but each
still needs a human read, which is what PARTIAL means.

The probe found two bugs in itself first, both of which had produced false
"missing" reports, and both caught by checking a finding instead of publishing
it:

1. Identifier names were matched as `[a-z0-9_]`, so `job-change-push` -- a
   quoted identifier with hyphens -- was read as a trigger called `job`, and
   two live push triggers were reported absent. MEMORY.md already records this
   shape: "Renamed guard reads as absent".
2. The catalog query asked only the `public` schema, so the `job_files`
   policies, which live on `storage.objects`, read as missing and
   `supabase_storage_patch.sql` was wrongly flagged.

Before that it could not run at all -- three Windows traps in a row (`npx`
ENOENT without `shell:true`, `npx.cmd` EINVAL under Node's hardening, and with
`shell:true` the shell split the SQL on spaces). `--canary` is what caught
every one of these: it plants an impossible object in every file, and any file
still reading LIVE means the checker is not asking.

**Two limits worth keeping in mind.** `UNJUDGEABLE` is not a pass -- a
data-only or grant-only migration cannot be judged by existence and those 21
need reading. And `LIVE` means the objects exist, never that this file's
version of them is what runs: a later file may have replaced a function body
wholesale. Proving that needs a body fingerprint, as r8 got.

## 2b. The apply turned up a DARK CHECK in live-rules-guard

The suite went red afterwards on one check in
`tests/live-rules-guard.test.mjs`: *"moving to the same stage returns false and
writes no 2nd event -- again=f events_before=0 events_after=0"*, while the
check above it, a crew account moving a sold job, stayed green. Those two
cannot both be right.

**The live function is correct.** Measured directly, as that test's own crew
fixture, in a rolled-back transaction:

| | |
|---|---|
| `sees_all_jobs()` | false |
| my crew records / visible jobs | 0 / 0 |
| `can_see_job(fixture job)` | false |
| `set_production_stage(...)` | **ERR 42501: This job is not assigned to you.** |

A first attempt at this measurement derived the crew's company by joining
profiles to the job, which can seat the crew in a different company from the
job and hide it for a reason that has nothing to do with this migration. The
second attempt used the test's own OWNER constant and **asserted** that the
job and the crew share a company before reporting anything.

**The test was wrong, and in a way worse than the red.** It plants a buggy
`set_production_stage` to prove a check can fail, then "undoes the plant" by
running a HAND-WRITTEN COPY of the function body. That copy predates this
migration, so from today it put back a body with no crew guard -- and every
check after it in that file was exercising code that is not what ships. The
same shape as MEMORY.md's "Transcription test never read its source".

Fixed three ways:

1. The restore now captures `pg_get_functiondef` BEFORE planting and replays
   it, then asserts the replay reproduced the captured text exactly. It cannot
   drift again.
2. The crew fixture now gets a crew record and the lead on both fixture jobs,
   because these checks are about the production-stage rules, not the scoping
   -- and it **asserts** it ended up on both, rather than assuming.
3. Two checks only asserted THAT an exception was raised, so they would have
   passed on "not assigned to you" instead of the reason they name. They now
   assert the reason, so the approval gate is still under test.

37 of 37. Each of the three changes was then deliberately broken and confirmed
to turn the test red -- the reason assertion showing 36 of 37, so exactly one
check caught it rather than the file crashing.
