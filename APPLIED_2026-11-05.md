### 5. New companies get a starting catalog -- and its silent-failure bug

`supabase_r20_seed_new_company_catalog.sql` PART 2. Eleven of the twelve
companies in production hold an empty catalog, and nothing gave a new one a
list: no trigger, no function, only a button almost nobody finds.

This file was held yesterday because its own dry run read 79/84. That one
unexplained failure is now settled, and it was a real defect, not a flaky
test. The failing check was:

> "...and the failure was written to app_errors, not fatal, naming the
> company, where the admin console will show it" -- want 1, got 0.

**What was actually wrong.** `app_errors` carries a BEFORE INSERT trigger,
`00_stamp_app_error_owner`. For any writer that is not the backend it
overwrites `company_id` with `public.current_company_id()` -- the CALLER's
company -- because a crash report filed by a signed-in person must not be
able to name somebody else's business. It CORRECTS rather than refuses, by
design, so the insert reports success either way.

During a sign-up that is fatal to this particular row. The seeding trigger is
AFTER INSERT on `companies`, and it runs BEFORE `create_company_with_owner`
has written the owner's `profiles` row -- so `current_company_id()` is NULL,
and the log row lands with a NULL company. Logged, and invisible in every
per-company view, which is the same as not logged at all. The seeding
trigger's handler turns any trouble into a bare `raise warning`, so nothing
surfaced.

**How it was settled, not guessed.** I ran the same trigger body with the
nested handler recording its outcome instead of swallowing it, in a
rolled-back transaction:

- a plain insert as the session role: insert succeeded, readback found **1**
- through `create_company_with_owner`, impersonated: insert reported
  **SUCCEEDED**, readback found **0**
- the trigger saw the same company id the function returned, and the company
  existed, so it was not an id mix-up
- the handler's own temp-table writes survived, so nothing rolled back
- and the planted failure's row was found with **company_id NULL**

**The fix**, in both copies of the function in the file: capture the new row's
id with `returning id into logged`, then put the company back with an UPDATE.
The stamp trigger is INSERT-only, so the correction sticks, and
`is distinct from` makes it a no-op on every path where the stamp left the
company alone. After the fix the dry run reads **80/84** and that check reads
want 1, got 1.

**The four remaining dry-run failures are accounted for and none is a
defect.** Three are the harness: it calls `admin_create_company` as a platform
admin, the CLI role is not one, and the two readbacks after it cascade off
that refusal. The fourth compares `net.http_request_queue` before and after --
and the dry run cannot queue anything itself: it never updates `companies` at
all, and the only HTTP trigger there is AFTER UPDATE with a WHEN clause on
`details_completed_at`/`welcome_sent_at`, columns the dry run never writes. So
that control is reading drift in a queue the live app fills and drains.

**Applied, and verified against a baseline taken first:** the function, the
trigger function and the trigger are present and enabled; the live body
carries the fix and is SECURITY DEFINER with its search_path pinned; and no
existing company was given a single row -- 130 catalog rows before and after,
with the per-company checksum identical (10c2220b0f0933b4d0021a6640256b58).
A negative control in the same probe returned 0, so the present/absent counts
mean what they say.

### 7. A record of what has been applied, and a runner that keeps it

Until today nothing recorded which SQL files had run. The live database was the
only place the answer existed, and reading it took a query per migration. That
is why the deposit rule sat dead for six weeks and why r20, r42 and
crew_job_scope each had to be found by interrogating production.

**`public.schema_migrations`** (`supabase_r63_migration_ledger.sql`) --
filename, sha256, origin, applied_at, applied_by, notes. 12 proofs, 4 of them
canaries. It is built around the trap this project has hit before: Supabase
grants every new public table to `anon` and `authenticated` on creation, so the
grants are revoked explicitly AND RLS is on with no policy -- two layers,
because each one alone has gone wrong here. A ledger a client could write is
worse than one it could read: a forged row makes the runner skip a migration
for good.

`origin` is not a boolean on purpose. **applied** means the runner ran the file.
**adopted** means it was recorded WITHOUT running, because it predates the
ledger and the schema already reflects it -- an honest "assumed, never
verified". It stops 208 historical files being re-run, and never claims they
were proven.

**`scripts/apply-migrations.mjs`** -- read-only by default; writes nothing
without `--yes`.

```
node scripts/apply-migrations.mjs                 report
node scripts/apply-migrations.mjs --apply --yes   run every pending file, in order
node scripts/apply-migrations.mjs --apply --only <file> --yes
```

Two refusals are the point of it:

- **A file whose checksum changed since it was recorded stops the run before a
  single statement is sent.** Editing an applied migration in place is how two
  databases silently stop matching. Proven, not assumed: I appended one comment
  line to r63, and the runner named the file, printed recorded ff834c558afc ->
  now e35d49a275c4, refused to write and exited 1. Then I restored it and the
  report went clean again.
- **A file that is not in apply-order.txt cannot be applied.** It refuses and
  tells you to place it, so the order list cannot drift the way it already had.

State now: **212 files in the order, 212 recorded (4 applied, 208 adopted), 0
pending.** Adoption is one statement rather than 208 round trips, so it records
all of them or none.

### 9. The sandbox tenant

**Not a new table.** You suggested one; it would not have worked. The app and
the office read dozens of tables, so a parallel copy means a switch in every
query in both and a copy that drifts -- this project already ran a hardcoded
table list thirteen tables stale. A second COMPANY needs none of that: the
platform is already multi-tenant and its isolation is already audited. The same
RLS that stops PeterLLC seeing Legacy Solutions' jobs is what separates a
sandbox. No second project, no second bill.

**The four ZZ TEST companies are now sandboxes** (`is_sandbox = true`). They
were the right choice rather than a fresh empty company, because
`ZZ TEST — Busy season, jobs in every state` already carries jobs in every
state and now a 92-row catalog -- the "same data" you asked for already exists.
None of the four held a mailbox or a payment connection, so none had to be
disconnected.

**The guards remove capability rather than checking each caller.** Six
transports in `supabase/functions` reach real people: Resend, Brevo, FCM,
Stripe, Square and SMTP. Adding a check to each caller is control-by-control
gating, which never converges -- the next function forgets it and nothing
fails. So two are closed by taking the capability away, which no future code
can forget:

- a sandbox company **can never hold a row in `mail_accounts`**, so it has no
  mailbox: no SMTP to a customer, no inbound sync, no reply
- a sandbox company **can never hold a row in `payment_connections`**, so it
  has no Stripe or Square credential: `create-payment-link` and
  `create-checkout-session` have nothing to charge with

A third guard refuses to flip a company INTO the sandbox while it still holds
either, because the two above only see new writes -- otherwise you would get a
sandbox with a live mailbox still attached, which reads as contained and is not.

`public.sandbox_refresh_from(source, target)` copies catalog and settings **one
way only** and refuses any target that is not a sandbox, so a transposed
argument cannot write into the real business. Jobs and customers are not
copied: that needs its table list derived from the schema rather than typed
out, and a typed list is the one that goes stale.

**Proven against the real sandbox company, not just throwaway probes:** giving
it a mailbox and connecting Stripe were both refused with this guard's own
message; refreshing from live copied 124 catalog rows; and refreshing the live
company *from* the sandbox was refused. The migration's own 12 proofs include
five canaries, two of which assert the identical insert goes THROUGH for a live
company -- without those, a wrong column list would have read exactly like a
working guard, and `mail_accounts` needs four columns where I first wrote two.

One control had to be corrected: my first attempt connected Stripe to Legacy
Solutions, which already holds a connection, so it hit the primary key and read
as the guard blocking live work. Re-done by picking the control company by
property -- not a sandbox, holding no connection -- with the candidate count
asserted first (6) so an empty pick could not pass as success. Both operations
then went through for a live company.

**Transactional mail is now closed too, and deployed.** Resend and Brevo need
no mailbox, so capability removal did not reach them; twelve functions call
those hosts directly. `supabase/functions/_shared/sandbox.ts` is the one place
to ask, wired into ten of them -- `mail-message` and `resend-inbound` are
covered by capability instead, since both resolve through `mail_accounts` and a
sandbox holds no such row.

The guard takes a company ROW rather than an id, so it adds no call and no
failure mode of its own: the caller selects `is_sandbox` beside the columns it
already reads. A row WITHOUT the column throws by name instead of reading the
absence as "not a sandbox" and sending. That protection paid for itself the
same day -- two test fixtures lacked the column and failed loudly rather than
quietly mailing. `invite-company` holds only an id, so it reads the flag, and a
failed read refuses rather than guessing. `admin-mail-send` filters its own
recipient list and refuses the WHOLE send if it cannot judge even one company,
because dropping the unjudged ones would mail nobody and report success.

`tests/a93-sandbox-cannot-reach-a-customer.test.mjs` is what fails when the
THIRTEENTH function forgets: it enumerates the senders from the source, so a
new one appears on its own and must either ask the guard or be named as covered
by capability, with a reason. Proven to have teeth -- a planted revert in
hoa-letter (call, column and import removed) turned it red, and restoring the
file turned it green.

Deployed 5 November 2026, after the suite read 273/273. Verified from the
artifact rather than the exit code: the deployed bundles were downloaded back
and the guard is present in them, the deployed `_shared/sandbox.ts` is byte for
byte the repo's (sha256 494953eb...), and a function that was not changed,
quote-view, carries neither the guard nor the column -- so the check
distinguishes.

Push is left alone with a reason rather than by omission: `device_tokens` carry
`company_id`, so a sandbox can only push to a device signed into the sandbox.
There is nobody else to reach, and a guard there would protect nothing while
reading like protection.

**To start using it:** mint a setup code for the sandbox company from the admin
portal, signed in as a platform admin, then claim it with a new login. I could
not do that step -- `admin_mint_setup_code` refused the CLI role with "Only a
FenceFlow admin may issue a product key", which is r42's own gate working, and
not something to bypass. Afterwards, `sandbox_refresh_from` tops its catalog up
from the live company whenever you want.

r64 was also the first file applied through `scripts/apply-migrations.mjs`, so
the runner is proven on a real migration and the ledger records it as applied.
